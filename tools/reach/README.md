# Reach combat project

Target: Halo Reach combat inside Steam Doom 3 BFG, using the owner's Steam MCC Reach installation as the asset source. First milestone: one assault rifle, quick weapon melee, independent frag throw, and sprint. Gameplay is reimplemented in BFG; this is not running the Halo engine inside Doom.

## Current status

Development branch: `reach-combat`. An opt-in sprint prototype is implemented: forward-only grounded sprint, weapon lowering, interruption on fire/zoom/reload, firing suppression during sprint and recovery, and a minimum charge to restart. Stock mode and multiplayer use the original running path. Sprint/recovery state resets on loading a save; existing serialized stamina is retained. No converted Halo assets or working Reach weapons are included yet.

Timed quick melee and grenade actions are now implemented for the next prototype build. `V` triggers a forward melee trace without selecting fists; `G` throws the installed BFG grenade without selecting its weapon slot. The actions share a cooldown, interrupt sprint, block firing/reload during windup and recovery, and cancel pending effects on weapon switching, cinematics, GUIs or death. A grenade is taken from the existing `ammo_grenades` pool only after its projectile shape has a valid launch position. Pending effects are cancelled on load; existing ammo/projectiles remain in the normal save stream. There is no grenade cooking in the quick action.

These actions use BFG's `damage_fists` and `projectile_grenade` as placeholders. The current gun lowers during the action; Reach punch/throw animations are not present. New weapon definitions can supply `def_reach_melee`, and the player definition can supply `def_reach_grenade` (a weapon definition with a `def_projectile` key), without copying the original game files into the repository. Timings, range and damage are tunable prototype values, not extracted Reach statistics.

The isolated sprint state-machine scenarios pass under GCC in C++98 mode. They check interruption/recovery, charge exhaustion, restart gating and reset behavior; they do not validate player physics, animations or game startup. The Windows workflow uses MSVC v143 and a signature-verified Microsoft DirectX June 2010 SDK download. The full Win32 Release build passed at commit `a7953c2`, producing `Doom3BFG.exe` in [GitHub Actions run 38198806764](https://github.com/davejohnson884/DOOM-3-BFG/actions/runs/38198806764). Compilation does not prove in-game readiness.

`reach_prototype.cfg` contains initial tuning, not authentic Reach stats. The isolated playtest launcher enables `g_reachLabAutoConfig` to reapply it after player spawn/load, because profile defaults reset bindings and player definitions reset the `pm_` variables. This lab option defaults off, so normal users can enable combat without overwriting their bindings. Launch-time `+set g_reachCombat 0` disables the prototype; remove the prototype config and restore your original movement/bind settings to restore the full stock configuration. Accurate Reach sprint speed, charge and recovery timing still require donor-data inspection or measurements.

The workflow keeps the SDK installation out of the checkout, verifies the SDK installer's Microsoft signature before extraction, and uploads logs even when the build fails. A successful build uploads `reach-bfg-win32`; do not replace your Steam executable yet. A backed-up lab installation and runtime smoke test come first.

The owner reports sprint, melee and grenade controls working after the readiness fix, but also reports freezes and a small window. The playtest launcher now defaults to borderless fullscreen at the primary desktop resolution and timestamped logging in mode 1. The engine's logging mode 1 now avoids a disk flush per print, as its documented behavior requires; mode 2 retains those diagnostic flushes. Runtime freeze diagnosis still requires a current log and whether the pauses recover or require closing the game.

The modern compiler adapter keeps the original warning level and diagnostics, but does not promote legacy warnings to errors. The original source predates MSVC warnings about member shadowing, specialization storage classes and inline allocation operators. Actual compiler/linker errors still fail the workflow, and the isolated sprint tests use warnings as errors. Source compatibility changes retain the VS2010 annotation path and use SAL on modern MSVC.

## Runtime and assets

The cloud machine cannot access your PC's Steam folders. Record the install paths for Doom 3 BFG and MCC using Steam Properties → Installed Files → Browse. Reach extraction must first be validated against those files. The existing Universal Modder Halo 3/Minecraft example is a useful reference, but does not establish that Reach first-person animations can be exported or converted.

Confirmed installs: BFG at `C:\Program Files (x86)\Steam\steamapps\common\DOOM 3 BFG Edition`; MCC at `D:\SteamLibrary\steamapps\common\Halo The Master Chief Collection`. Download this branch as a ZIP and extract it outside your Steam folders. Open `tools/reach` and double-click `Collect-install-info.cmd`. It creates a uniquely named JSON report containing file names, sizes and executable versions. It reads the game folders and changes no game files. Send the report to the project chat. The launcher's execution policy override is scoped to that one process; it does not change your Windows execution-policy settings.

The received inventory confirms BFG 1.0.0.2, `_common.resources`, `_ordered.resources`, and 44 Reach maps including `forge_halo.map`, plus the PC FMOD sound bank. The BFG folder also contains RBDoom/BFA executables; do not overwrite them. The owner's first playtest confirms startup and sprint/weapon lowering. The log showed startup defaults overwriting V/G and a failed unquoted config command. After reapplying the config, V/G lowered the gun. Source inspection found that lowering made the weapon fail readiness checks and cancel the effects. The fix allows the prototype's viewmodel lowering while retaining weapon-state and interruption checks. Actual melee damage, grenade launch and sustained sprint still need runtime validation, as does Reach asset conversion.

For the next development step, double-click `Collect-combat-data.cmd` in the same `tools/reach` folder. It reads only the two BFG resource containers and copies `.def`/`.script` text into a new private folder and ZIP beside the helper. Attach that ZIP privately to the project chat so the actual weapon/player script interfaces can be inspected. Do not publish or commit the generated data. The collector validates container bounds and paths, preserves duplicate entries by index, and excludes meshes, textures and sound payloads. It does not launch the game or change the game installation. Resource parser tests use synthetic containers; actual container compatibility is verified when the collector succeeds on the owner's files.

Keep extracted models, textures, sounds and animations outside Git. The intended distribution is source code, build artifacts and a local conversion tool; donor game data stays on the owner's PC. The first functional prototype should use BFG assets to validate controls and action timing before importing the Reach presentation.

Combat integration points: `neo/d3xp/Player.cpp` (`Weapon_Combat`, `PerformImpulse`, `AdjustSpeed`), `neo/d3xp/Weapon.cpp` (animation, melee and projectile events), and `neo/framework/UsercmdGen.h` (inputs). Script and weapon definitions live in installed game data and must be inspected before authoring replacements.
